Lesson 3: Introduction to BullMQ (Asynchronous Tasks)

In this lesson, we will explore what BullMQ is, why it is essential for cloud-native applications, and how it divides work between Producers and Workers.

1. What is a Message Queue?

In a standard web app, when a user makes a request (like registering), the server executes the code synchronously and returns a response. If the code does something slow—like sending an email or connecting to a third-party gateway—the user is forced to wait for that process to finish.

A Message Queue solves this. It lets you offload slow, heavy, or non-blocking tasks to run in the background. The server places a "Job" (or message) into a queue and immediately returns a success response to the user. A separate background process then pulls the job and runs it asynchronously.

2. Anatomy of BullMQ

BullMQ is a popular Node.js message queue library backed by Redis. It consists of three primary roles:

[ Producer ]  --(adds Job)-->  [ Redis Queue ]  --(pulls Job)-->  [ Worker/Processor ]
  • Producer: Your API controllers or services. They create jobs with a payload (e.g., { email: 'user@test.com', type: 'WELCOME' }) and add them to a named queue.
  • Queue (Redis): Redis acts as the fast, in-memory data store that holds the jobs, tracks their states (active, completed, delayed, failed), and guarantees that no jobs are lost.
  • Worker/Processor: Background Node.js processes. They listen to a queue, pick up jobs, execute the business logic (like calling an SMTP server), and mark the job as finished.

3. Why Use BullMQ? (The Core Utilities)

BullMQ provides several essential production utilities out-of-the-box:

  • Resiliency & Retries: If a background worker fails (e.g. because an external email provider is down), you can configure BullMQ to retry the job 3 times with exponential backoff (waiting longer between each retry).
  • Rate Limiting: You can limit the number of jobs processed per second to avoid getting blocked by third-party APIs.
  • Repeatable/Scheduled Jobs: You can set up cron-like schedules (e.g., "Run this cleanup task every 15 minutes"). We used this in Phase 1 for our event-lifecycle repeatable job to automatically mark past-due events as completed.
  • Decoupling: The API server doesn't need to know how to send emails or run lifecycle cleanups; it only needs to know how to add jobs to the queue. The worker handles the rest.

4. Our Codebase Reference

Here is how we added a welcome verification email job during user registration:

// 1. The Producer adds a job to the email queue:
await this.emailQueue.add(
  EmailJobType.VERIFICATION_EMAIL,
  { userId: user.id, email: user.email, verificationToken },
  { attempts: 3, backoff: { type: 'exponential', delay: 5000 } }
);

// 2. The Worker listens and processes the job:
@Processor(QueueName.EMAIL)
export class EmailProcessor extends WorkerHost {
  async process(job: Job) {
    if (job.name === EmailJobType.VERIFICATION_EMAIL) {
      // Send email simulation
      console.log(`Sending email to ${job.data.email}`);
    }
  }
}
