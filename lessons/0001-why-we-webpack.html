Lesson 1: Why We Webpack (Bundling in a Monorepo)

In this lesson, we will explore why we enabled Webpack in NestJS, what dependencies we added, and the mechanics of monorepo bundling.

1. What is Webpack?

Webpack is a static module bundler. In modern JavaScript/TypeScript, files import other files (using CommonJS require or ESM import). Webpack traces the graph of imports starting from an entry file (e.g. src/main.ts) and aggregates them into one or more bundled files (like dist/main.js).

2. The Problem: Nested Dist Directory

In a standard monorepo workspace:

eventify/
├── apps/
│   └── api/ (imports from packages/shared-types)
└── packages/
    └── shared-types/

By default, the TypeScript compiler (tsc) compiles files individually. Because apps/api imports a file outside its own folder (packages/shared-types), TypeScript shifts the base output directory structure to include both folders, producing: 

apps/api/dist/
├── apps/
│   └── api/
│       └── src/
│           └── main.js  <-- Actual Entrypoint
└── packages/
    └── shared-types/

But NestJS CLI expects the entrypoint directly at dist/main.js. This mismatch crashes the startup process because Node.js cannot find dist/main.

💡 The Webpack Solution
By enabling Webpack in nest-cli.json, Webpack bundles the entrypoint and its dependencies, creating a single, flat dist/main.js file instead of preserving folder structures.

3. The ESM Resolution Crash (Node 22)

When Webpack compiles the server, by default it treats local workspace packages (like @eventify/shared-types) as externals. This means Webpack outputs a standard reference:

const shared_types = require("@eventify/shared-types");

At runtime, Node 22 resolves @eventify/shared-types to the raw source file packages/shared-types/src/index.ts. Because Node 22 has native TypeScript stripping support, it attempts to load that file directly. However, Node's native TS execution handles TypeScript files as ES Modules (ESM).

In ESM, relative imports must include explicit file extensions. But our index file imported the enums extension-less:

export * from './enums/role.enum'; // Missing '.ts' or '.js' extension!

This caused Node to throw ERR_MODULE_NOT_FOUND.

4. The Fix: webpack-node-externals and inline-bundling

To fix this, we need Webpack to inline-bundle @eventify/shared-types directly inside dist/main.js, so Node never loads the raw .ts source file. We did this by customizing Webpack in webpack.config.js using the webpack-node-externals plugin:

const nodeExternals = require('webpack-node-externals');

module.exports = function (options, webpack) {
  return {
    ...options,
    externals: [
      nodeExternals({
        // Do not externalize @eventify/shared-types, so Webpack bundles it inline
        allowlist: ['@eventify/shared-types'],
      }),
    ],
  };
};

By placing @eventify/shared-types in the allowlist, Webpack bundles it inside the final dist/main.js, resolving the extension-less paths correctly at compilation time using Webpack's resolver.
